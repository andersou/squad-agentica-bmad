O problema

Um assistente sozinho escreve código, mas não sustenta um projeto

Onde um chat genérico vai bem
  • Escrever funções isoladas
  • Corrigir erros de compilação
  • Refatorar trechos de código
  • Acelerar protótipos
Onde ele se perde
  • O contexto some entre sessões
  • Decisões de arquitetura mudam a cada prompt
  • Sem critério de aceite, sem estratégia de testes
  • Ninguém lembra por que algo foi decidido

O problema não é o modelo. É a falta de estrutura em volta dele.

Por quê02 / 30

(~1,5 min) Pergunte: quem aqui já usa IA para codar? E quem já sentiu que o projeto desandou depois de algumas semanas?

Lado esquerdo: o chat genérico é ótimo em tarefas isoladas. Lado direito: o problema aparece quando o projeto cresce — o contexto some, decisões mudam a cada prompt, ninguém lembra o porquê.

Feche com a frase de baixo: o problema não é o modelo, é a falta de estrutura em volta dele.

Conceito

Squad agêntica é um time de papéis, não um chatbot

01

Papéis

Cada agente tem uma responsabilidade e um menu próprio de workflows: analista, PM, arquiteto, UX, dev.

02

Artefatos

Brief, PRD, arquitetura e stories ficam em arquivos versionados. Cada documento vira o contexto da fase seguinte.

03

Gates

Você revisa e aprova antes de avançar. Checagens como o gate do sprint planning e o code review seguram a qualidade.

O BMAD-METHOD é uma implementação open source desse modelo. O humano continua decidindo; os agentes executam com contexto.

Por quê03 / 30

(~1,5 min) Defina squad agêntica com três palavras: papéis, artefatos e gates.

Papéis: cada agente tem um foco, como num time real. Artefatos: o que um agente produz vira o contexto do próximo — isso substitui a memória do chat. Gates: você aprova antes de avançar.

Reforce: o humano continua decidindo. O BMAD é uma implementação open source desse modelo, e é ela que vamos ver.

03 · Dia a dia · fonte: docs/build/build-a-change.md19 / 30

(~2 min) Uma vez por projeto: o bmad-sprint-planning, que agora abre com o gate e só depois gera o sprint-status.yaml.

Depois o ciclo, por story e num chat novo: o bmad-build investiga, escreve a spec, implementa e já faz uma rodada de revisão, deixando a story em review. O bmad-code-review faz a revisão independente e fecha a story.

No fim de cada épico, a retrospectiva. Frase para fixar: duas sessões por story, uma para construir e outra para revisar.
